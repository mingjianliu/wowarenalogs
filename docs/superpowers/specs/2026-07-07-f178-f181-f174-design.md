# Design: F178 Matchup Intel Card, F181 Analysis Export, F174 First-Death Forensics

Date: 2026-07-07 · Branch: `feature-triage` · Status: approved direction, spec for implementation planning

Three independent features from TRACKER.md, implemented in order F178 → F181 → F174, each as its own commit series. Scope decisions made with the user:

- **F178**: offline version only — card renders on a completed match's report page; NO parser `arena_match_started` event, no live pre-match popup (that is a possible follow-up).
- **F181**: local export only (Markdown v1) — no hosted share page (blocked on hosted-web decision + CC BY-NC-ND license). PNG share card is phase 2, documented here but not built now.
- **F174**: the S3 first-death forensics entry (not the same-numbered leaver-shuffle item). Phases 1+2 only — deterministic features + rule-based bucketing. Phase 3 (LLM labeling, coaching priors) is a later project.

---

## F178 — Matchup Intel tab ("对阵情报")

### Purpose

On a finished match's CombatReport, answer: *next time you queue into this comp — what does their kill window look like, what should you hold, what should you track.* Everything on the card is derived from this match's own data (per the no-comp-heuristics principle: data-derived causal facts, never pre-encoded comp rules).

### Components

1. **`packages/shared/src/utils/matchupIntel.ts`** — pure data module, no React.
   - Input: `AtomicArenaCombat` (+ the viewer's player id for "your defensives").
   - Output: `IMatchupIntelCard`:
     - `enemyComp`: enemy spec list (via `specToString`) + match result.
     - `killWindows`: from `reconstructEnemyCDTimeline(...).alignedBurstWindows` — per window: threatLabel, participating CDs (player + spell), duration, dampening, healerCCed.
     - `enemyCDInventory`: per enemy player, offensive CDs actually cast this match with their cooldownSeconds (from `IEnemyPlayerTimeline`).
     - `holdList`: per kill window, the viewer's defensive cooldowns that were available at window start vs already spent (reuse defensive classification from `cooldowns.ts` / `spellEffectData`), plus defensives cast outside any window (stated as facts, not verdicts).
     - `trackList`: enemy CC casts on the friendly healer inside kill windows.
2. **`packages/shared/src/components/CombatReport/MatchupIntel/index.tsx`** — renders the card sections.
3. **`CombatReport/index.tsx` + `CombatReportContext`** — add `matchup` to the activeTab union and tab bar, following the existing tab pattern. No feature flag for v1 (deterministic, cheap, no API calls).

### Error handling

- No burst windows detected (the F44 29% case): render the rest of the card with an explicit "本场未检测到爆发窗" notice — never a blank section (F180 philosophy).
- Non-arena / malformed combat: tab hidden (same gates the other tabs use).

### Testing

- Unit tests for `matchupIntel.ts` against existing test logs (shared `__tests__` pattern, `npx tsdx test`): comp extraction, window mapping, hold-list availability math, the no-windows empty case.

## F181 — Analysis export (v1: Markdown)

### Purpose

One match's AI findings + verified comparison as a paste-able artifact for a teammate / coach / stream chat. Local only; nothing is published anywhere.

### Components

1. **`packages/shared/src/components/CombatReport/CombatAIAnalysis/exportAnalysis.ts`** — pure serializer.
   - Input: the findings array, the verified-comparison result, match metadata (comp, map, result, duration, date, viewer spec).
   - Output: a Markdown string — header (matchup + result), findings with timestamps and evidence lines, compare section with cohort label exactly as shown in the UI (the honest per-selection cohort label from `9188eee2` must pass through verbatim — the export must not re-summarize or invent cohort claims).
2. **Export buttons** in the CombatAIAnalysis header, rendered only when an analysis result is present:
   - **复制 Markdown** — `navigator.clipboard.writeText` (works in Electron renderer and web).
   - **保存 .md** — Blob + anchor download, filename `wal-analysis-<date>-<comp>.md`. No nativeBridge changes needed.

### Phase 2 (documented, NOT in this implementation)

PNG share card: a dedicated `ShareCard` component rendered off-screen, captured via a new nativeBridge method using Electron `webContents.capturePage` (desktop only; web keeps Markdown). The serializer/renderer split in v1 is the seam a future hosted share page would reuse.

### Error handling

- No analysis loaded / analysis failed: buttons not rendered.
- Clipboard API rejection (permissions): fall back to triggering the .md download and telling the user.

### Testing

- Snapshot tests for the serializer (typical findings + compare, findings-only, compare-missing).

## F174 — First-death forensics, Phases 1+2

### Purpose

First blood ≈ the round (die-first WR 1.0%, mate-first 0.7%, no-deaths 100%, n=1151 — auditUnknowns #5). Classify the 15 seconds before every first death in the corpus into a deterministic cause taxonomy, per spec.

### Components

**`packages/tools/src/auditFirstDeath.ts`** + npm script (`audit-first-death`), following the `auditBurstTimeline.ts` pattern: iterate `forEachCorpusGame` (healerOnly default — the corpus is healer-POV and several features reference the owner-healer).

**Phase 1 — per-game deterministic features.** First death = earliest `deathRecords` entry among player units; window = `[t−15s, t]`. Record victim identity (friend/enemy, spec, is-owner) and:

| Feature | Source |
|---|---|
| `healerCCLocked` | CC aura events on the owner within the window (reuse existing CC classification from the timeline utils); total CC-locked seconds |
| `enemyBurstActive` | any `alignedBurstWindow` overlapping the window (`reconstructEnemyCDTimeline`) |
| `victimDefensivesUnused` | victim's known defensives (`spellEffectData` defensive types) with no cast in the window; conservative — "not cast" only, no availability guessing beyond earlier-cast CD math |
| `healerGcdIdle` | owner max inter-cast gap ≥ 3s within the window while the victim is <60% HP |
| `healerManaPct` | owner mana at window start (advanced-logging resource fields, same read as `resourceSnapshot`) |
| `victimFocused` / `victimSwappedTo` | share of enemy damage into the victim ≥ threshold; swap = enemy damage-majority target changed to the victim inside the window |

Output: JSONL (one line per first death: file, combatIndex, victim, features) under `scratch/first-death/` + console summary counts. If a run cannot finish, report the games completed — never backfill (eval-integrity rule).

**Phase 2 — rule-based bucketing.** Deterministic decision list, first match wins:

1. `healerCCLocked` (≥ threshold seconds) → **A: healer CC-locked at the kill**
2. `victimDefensivesUnused` ∧ `enemyBurstActive` → **B: victim held defensives into a burst**
3. `enemyBurstActive` ∧ `victimFocused` → **C: coordinated focus, defensives spent**
4. `healerGcdIdle` → **D: healer idle during the collapse**
5. else → **UNCLASSIFIED** (reported as such, with count)

Report: per-spec cluster distribution + per-cluster round win rate, written to `docs/analysis/<run-date>-first-death-forensics.md` (dated the day the audit runs). All numbers are measured metrics; no LLM calls, no scores, no `healer-eval/**/scores/` output.

### Testing

- Unit tests for each feature extractor against a fixture log (tools `__tests__` pattern). Bucketing is a pure function over the feature record — table-driven tests.
- Thresholds (CC-locked seconds, focus share, idle gap) are named constants at the top of the tool with the audit date, so a re-run after tuning is reproducible.
